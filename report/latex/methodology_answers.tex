\subsection{Answer Production and Model Configuration}
\label{subsec:answer_production}

FinTrace separates numerical answers, definitions and narrative questions because each requires different checks~\cite{fintraceRuntime2026}. For supported numerical requests, the backend binds the requested measure to extracted source cells. Company, year, unit, reporting basis, operational scope and report version remain attached to each value. Python presents the values through templates and performs compatible comparisons using decimal arithmetic. Absolute change is the later value minus the earlier value; relative change divides that difference by the earlier value. Changes in percentage-valued measures are reported in percentage points, with basis points where supported. The language model does not calculate the financial result. A general profit question can return labelled alternatives rather than forcing users to know the terminology first. Only variants actually bound to the source are shown.

Definitions use report evidence with bounded local-model paraphrasing and automated support checks. Narrative questions take a different route: lexical search supplies passages, Qwen selects evidence identifiers, and Python displays quotations from those passages. The active configuration uses \texttt{source\_selection} mode, not unrestricted synthesis. Identifier and quotation checks prevent invented passages, but do not establish that a selected passage is relevant or sufficient. For mixed questions, a successful numerical part must not conceal an incomplete explanation.

The configured local model is \texttt{qwen3:8b} through Ollama, using the recorded Q4\_K\_M quantised distribution~\cite{qwenOllama}. The project did not train or fine-tune it. Its configured context is 16,384 tokens; task-specific output caps and sampling settings are retained in Appendix~\ref{app:runtime_details}. A 35-second timeout applies per call, not per whole question. Conservative byte limits also constrain evidence packing~\cite{fintraceRuntime2026}.

Early local-model experiments and a small Groq-hosted comparison informed the choice, but exposed examples do not demonstrate general model superiority. Development assessments also showed that fluent generation could preserve an upstream wrong-metric selection. Numerical generation was therefore removed while financial-context checks were retained. Local inference avoids per-token provider charges but consumes hardware resources and can have cold-start delays. When evidence is insufficient, the response describes the limitation rather than claiming the full report lacks an answer. Model self-review remains a fallible automated check, not independent verification.
